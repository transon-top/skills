# 簇三 检出已有问题

覆盖三个要点：**测你的测试**、**找死代码**、**找重复**。三者都是"事后检出"——代码已经写出来了，回头找里面藏着的东西。

## 变异测试（测你的测试）

coverage 只告诉你某行**跑过**，变异测试才告诉你测试**会不会发现这行坏了**。绿色测试不等于有人做过判断。

### 四类"存活变异体"信号

存活变异体 = 代码被改坏了但测试仍然通过。它指向的是测试本身的形状缺陷：

1. **Shape instead of content** —— `toHaveBeenCalled()` 而不是 `toHaveBeenCalledWith(...)`；`toBeDefined()`；`toHaveLength(3)` 但没人看列表内容
2. **未经验证输出生成的 snapshot** —— 会把已有 bug 固化成期望结果
3. **断言复述实现** —— 测试与代码同样错、错得一致，于是都通过
4. **检查 mock 而不是代码** —— 断言 mock 被调用过，而不是被测代码产生了什么效果

变异算子的例子：把 `<` 翻成 `<=`、清空数组字面量、反转条件、交换返回值。

### 配置要点

**不要设置失败阈值。** equivalent mutants 永远存在，有价值的测试可能完全不推动分数；分数一旦成为目标，写出来的就是"为杀变异体而写"的测试。**当检测器，不当 KPI。**

### 成本

作者项目约 **4,700 mutants**，增量运行约 **6 分钟**。所以：

- 默认限定 `mutate` 范围，不要每次全仓扫描
- 配合持久化的增量文件，否则每次都是全量

配置细节 → `tools/stryker.md`。

## 死代码

AI 加代码远比删代码容易。没有自动删除检查，未使用的文件、导出、依赖会持续累积。

`knip` 找三类：没人 import 的文件、没人用的 export、不再需要的依赖。接入成本低（"takes little effort to add to an existing project"）。

**`ignore` 列表会增长，必须定期复查**——每个被忽略的路径就是"被明确告知不要检查"的一部分代码。ignore 列表的增长速度是检查有效性的反向指标。

### 通用工具盖不到的部分自己写

两个具体缺口：

**可达性 ≠ 被 import 过。** knip 问的是"这个东西有没有被 import"，自写脚本问的是"它从运行中的应用出发能不能到达"。后者知道你的别名、生成 client、设计系统约定，所以能发现"被 import 了但那条路径本身是死的"。

**过期的 `vi.mock()` 声明。** mock 已经与被测代码不匹配但测试仍然通过。TypeScript 只把模块路径当字符串，linter 只看到函数调用，coverage 仍然报覆盖——三方都不管这个缺口。

### 自定义检测器必须自带测试

这些检测器常由**被它们监管的同一个 AI** 写。静默漏报会造成虚假信心——检查显示绿灯，而它根本不工作。

最低要求：**用一个故意写死的文件测试检测器，它必须能找到**。

配置细节 → `tools/knip.md`。

## 重复代码

AI 倾向再写一份实现，而不是去找已有的——搜索大仓库耗时、耗 token，且不保证搜到。

**重复本身不是罪，风险是两份开始分叉。** 作者遇到的例子：同一个 payroll 总额，一处显示 23h30m，另一处显示 0h00m。

### 配置要点

文章原话：**"The important configuration is to use different thresholds for markup and logic."**

重复的 JSX 可能是有意的（结构相似的列表项、卡片）；重复的业务逻辑更可能成为维护问题。所以 markup 阈值放宽、logic 阈值收紧。具体怎么在配置里实现 per-format 阈值 → `tools/jscpd.md`。

### 局限

jscpd 只找**文本级**重复。两份分别写出来、规则相同但看着完全不同的实现，它看不见。语义重复仍需人工 review。

配置细节 → `tools/jscpd.md`。

## 三者与基线策略的关系

这三个工具首次接入时**默认只报告、不阻塞**（不进 `check` 的失败路径）。存量问题不是这次要清的——清存量会让技能输出一份没人看的报告，且与渐进策略冲突。先让它跑起来、报告数字，再逐步收紧。
