# 簇四 面向模型的防护与规范注入

对应要点 6「Put the rules in front of the model」。前面所有检查都是**事后**的；这一簇尝试把规则放到**模型生成时**的面前。

## 两个手段

- **`react-doctor`**（仅 React）：可作项目扫描，也可装成 skill 让 agent 在写代码时就能看到问题。用法 → `tools/react-doctor.md`
- **项目规范文件**：`CLAUDE.md` / `AGENTS.md`，本技能注入的那块内容

## 注入内容的边界

注入进项目规范的是**这个项目的事实**与**写给这个项目的指令**。本技能自身的东西一律不写：

- 技能名、技能文件路径、"本技能范围内 / 范围外"这类边界声明
- 其他技能的名字（`/setup-pre-commit`、`/frontend-test-setup`）
- 工具出处、文章链接、技能内部的设计理由

读这份规范的是**下一个在本项目里写代码的 agent**——它不知道也不关心规范由谁注入。把技能层的账记在项目头上，就是注入污染：项目文档里出现别的东西的名字，读者只能忽略它，而每一次"这跟我无关"都在削弱整份规范的可信度。

判断标准一句话：**这句话删掉之后，项目本身是否少了信息？** 少了就留，没少就是噪声。

---

## 必须写进规范的两个前提

不写清楚这两点，注入的规范会被当成噪音：

### 1. 预防是概率性的

规则文件每次会话只被读一次，要跟 40 行其他内容和模型权重里的百万个仓库竞争。它**只能降低错误频率，不保证任何事**，并且**不取消**任何一项事后检查。

写成"AI 必须遵守"会给人错误的安全感；写成"这些是常见失败模式，写完自查"才符合实际。

### 2. 分数是诊断，不是目标

这类工具常给一个跨 security / perf / architecture 的**单一分数**。文章原话："Treat that score as a diagnostic, not a target"。

分数一旦成为目标，agent 会为数字优化而不是为代码质量优化——删掉难写的代码、加上无意义的断言，分数就上去了。变异测试分数同理。

---

## 本技能自己的事（不写进规范）

更彻底的做法是把防护从规则文件移入 hooks——对变更文件跑 linter，"same session, same feedback loop, no competition for attention"（同一会话、同一反馈回路、不与其他内容争夺注意力）。但把防护移入 hooks 是另一件事：**本技能不写 `.claude/settings.json`**（见 SKILL.md 边界表），pre-commit 类钩子归 `/setup-pre-commit`。这属于技能分工，只影响本技能做什么，不进项目规范。

---

## 注入模板

用 managed markers 包裹，按用户勾选的簇拼装内部块。**未勾选的块不写进去**。

````md
<!-- FRONTEND_GUARDRAILS_START -->

## 代码护栏

这些检查只降低错误频率，不保证任何事，也不替代人工 review。

### 类型

- 后端响应类型从 `<spec 位置>` 生成，生成目录不手改；spec 变更后重跑 `<生成命令>`
- 响应在运行期用 Zod 校验后再用

### 代码规则

- 写完跑 `<lint 命令>`。规则挡路时改代码，或调规则级别并写明理由——`eslint-disable` 会让检查失去覆盖面
- 派生值、状态同步、响应 prop 变化在渲染期算或放进事件处理，不用 `useEffect`
- 类型报错补真实判断，不写 `!` 消掉
- 测试必须有断言，提交前清掉 `.only`

### 分层

```text
<按用户确认的层填写：目录 + 依赖方向>
```

### 检出

- `<knip 命令>` 找未使用的文件 / 导出 / 依赖
- `<jscpd 命令>` 找重复代码——写新实现前先搜已有
- 两者只报告不阻塞，数字是基线。**分数是诊断，不是目标**

### 规则维护

新规则以 `warn` 进入：抓到真实 bug 升 `error`，一个月只有噪声就关掉。加规则要有事故依据。

<!-- FRONTEND_GUARDRAILS_END -->
````

## 拼装规则

- 只写用户勾选的簇对应的块
- 命令字符串用项目实际的 package manager 与 script 名（`pnpm lint` / `npm run lint`）
- 分层那块**必须来自用户**，不代人臆造
- 若项目已有 `docs/` 下的规范文档，把完整版本放那里，`CLAUDE.md` 只留短引用 + marker
- **拼完逐句过一遍「注入内容的边界」的删除测试**：这句话删掉之后，项目本身是否少了信息？没少就删掉。技能名、其他技能名、技能文件路径是这条测试的常见漏网项——它们读起来像"补充说明"，实际只是技能层的事
- **注入块每次会话都进上下文，按最小必要写。** 三类最常见的冗余：技能层的设计理由（"为什么规则文件不如 hooks 可靠"）、验证过程的记录（"已用 `--showConfig` 确认生效"）、同一意思在相邻两段各说一遍。命令、路径、层定义、项目的已知坑保留；解释为什么这么设计的删掉

## 文件选择

- 只存在 `CLAUDE.md` 或只存在 `AGENTS.md` → 注入存在那个
- 都存在 → 查两份职责，放最合适的一处，另一份只加短引用
- 都不存在 → 创建 `CLAUDE.md`（用户要求 `AGENTS.md` 则创建它）

再次运行只替换 marker 之间内容，不追加新的一份，不覆盖用户原有内容。
