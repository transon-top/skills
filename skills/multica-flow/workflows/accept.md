# 人工验收

> 进入：「交付审查」无质疑（或质疑已闭环），合并请求已在本地验证分支。本地人工验收 + 迭代补充；验收结论落平台。

## 分支就位

- 已在合并请求分支 → 直接验收
- 新会话直入且不在验证分支 → 拉取合并请求到本地（同「交付审查」拉代码：GitHub `gh pr diff` / GitLab `glab mr diff` / fetch 后切分支）

## 本地迭代（可选）

- 用户在本地自行补充和迭代；改动提交后 push 到远程合并请求分支（成为合并请求一部分，agent 可见）
- 只留本地不推 → 合并时改动丢失；合并前必查远端同步（`git fetch` + `git status -sb`），未推的提交提示处理

## 干净检查

- `git status --porcelain` 空 = 无未提交改动
- 停在合并请求分支时相对 main 有差异属正常，别误判为脏
- 有未提交改动：提示处理（stash 或提交），不留脏状态到验收

## 验收判定

- **通过** → 评论固定格式落 issue：「人工验收通过，准予合并」（评论类，走确认门全文预览 + 目标 thread）——这是后续会话路由「合并收口」的匹配信号；询问立即合并还是稍后，立即 → 出口「合并收口」
- **不通过** → 分析问题根源、是否属于当前合并请求范围，列出处理路径与理由，用户定夺：
  - 属当前合并请求范围 → 随本次返工一起处理，走「质疑确认」
  - 不属 → 单独指派子任务（新 issue 走「明确需求」）
  - 每条路径附理由与影响

完成：验收结论已定并落平台（通过 → 信号评论在 issue 里；不通过 → 问题清单与路径已定），无脏状态
